## Ticket 2 — Supabase project setup and schema migration

**Deviation:** `schema.md`'s RLS section gives explicit `select`/`insert`/`update` policies only for `ingredients` (with an instruction to copy the same three-policy shape to `recipes` and `log_entries`), plus `select`/`update`/`delete` for `groups`. It does not give any policies at all for `profiles`, `weight_logs`, or `group_invites`, doesn't give `group_members` policies beyond "enable RLS", and doesn't give `delete` policies for `ingredients`/`recipes`/`recipe_ingredients`. The migration (`supabase/migrations/20260819000000_phase1_schema.sql`) fills these gaps with:
- `profiles`: select own row or a fellow group member's row; update own row only.
- `weight_logs`: select/insert/update own rows only (personal, no group scope — matches Progress being individual-only per ticket 18).
- `groups`: added an `insert` policy (`owner_id = auth.uid()`) since none was given and group creation needs one.
- `group_members`: select rows in any group the caller belongs to; delete restricted to the group's owner. No client-side insert policy — membership rows are created via the group-creation flow and the `accept_group_invite` RPC (`security definer`, bypasses RLS).
- `group_invites`: select/insert restricted to the inviting group's owner. No update — `accepted_by`/`accepted_at` are set only via the `accept_group_invite` RPC.
- `ingredients`, `recipes`, `recipe_ingredients`: added `delete` policies mirroring the existing ownership pattern (needed for ingredient delete in ticket 6, and removing an ingredient from a recipe in ticket 7).

**Why:** The acceptance criteria for this ticket require RLS enabled on every table listed in `schema.md`, and the app can't function (profile reads, group creation, ingredient delete, etc.) with RLS enabled but zero policies on these tables. All new policies extend the existing "personal row owned by caller, or caller is a member of the owning group" pattern already established in the doc rather than introducing a new access model.

**Not yet verified:** This migration has not been applied to a live Supabase project or manually tested against two accounts (agent tooling restrictions in this session prohibit connecting to any database). Applying it, running it, and doing the manual cross-user/cross-group RLS check are left as a manual follow-up — see `supabase/README.md`.

**Deviation (env/deploy tooling):** `schema.md`/`phase-1-tickets.md` don't specify how Supabase credentials should be configured or how migrations get pushed to a given environment. Added `.env.dev` / `.env.prod` (gitignored, with `.env.dev.example` / `.env.prod.example` templates committed) holding `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_PROJECT_REF`, and `SUPABASE_ACCESS_TOKEN` per environment; Vite picks the right file via `--mode dev`/`--mode prod` (wired into `npm run dev` / `build` / `build:dev`); and two new npm commands, `supabase:push:dev` and `supabase:push:prod`, run `scripts/supabase-push.sh` to `supabase link` + `supabase db push` against the matching project. **Why:** requested directly (not part of a numbered ticket) to give dev/prod Supabase projects a repeatable, one-command way to receive schema pushes. Not yet run against a live project for the same database-connection reason as above.

## Ticket 5 — Onboarding flow

**Deviation:** `rpcs.md` has no entry for onboarding submission. Onboarding writes span two tables — `profiles` (name/height/goal fields) and `weight_logs` (the first weight entry) — which must succeed or fail together, matching this doc's own decision rule ("multi-table writes that must succeed or fail together -> Postgres RPC function"). **Deviation:** The onboarding submit calls this RPC directly against Supabase rather than going through the Dexie/outbox write path described in `frontend-architecture.md`. This mirrors how the auth feature (Ticket 3) already writes straight to Supabase (`signUpWithEmail`, `signInWithGoogle`, etc.) — onboarding happens immediately post-signup, before there's any reason to assume the device is offline, and `weight_logs` isn't part of the Dexie mirror in `frontend-architecture.md` in the first place (it's only needed for Progress, a separate ticket). The local `profiles` Dexie table is also not updated here, since the pull/sync engine (`src/sync/`) doesn't exist yet as of this ticket.

**Deviation:** `frontend-architecture.md` documents `useAppStore`'s `AppState` as `{ userId, activeGroupId }` plus their setters. **Not yet verified:** Same database-connection restriction as Tickets 2/3 — this session's tooling can't connect to a database, so the migration hasn't been pushed or exercised against a live project. **Deviation (added after initial review — calorie target calculation):** Requested directly: onboarding now also computes and stores a daily calorie target (Mifflin-St Jeor BMR -> activity-scaled TDEE -> goal-adjusted target), and is presented as an MUI `Stepper` (5 steps: about you, body metrics, activity level, goal, calorie target) instead of the single flat form described above. This required collecting three fields beyond the original ticket's scope (`height`/`weight`/`goal weight`/`goal type`):
- `birthdate` (replaces a raw "age" input — stored so a future yearly cron can recompute `daily_kcal_target` as age changes, without the user re-entering anything; no such cron is built yet, this only lays the data model for it).
- `sex` (`biological_sex` enum: `male`/`female`) — not requested, but Mifflin-St Jeor requires it for a correct BMR; omitting it would silently produce wrong calorie targets for one sex.
- `activity_level` (enum: `sedentary`/`light`/`moderate`/`very_active`/`extremely_active`) — needed to scale BMR into TDEE.

For `lose`/`gain` goals, the calorie-target step presents two computed presets — "Steady" (TDEE × 0.85 lose / × 1.15 gain) and "Aggressive" (TDEE × 0.75 lose / × 1.25 gain) — each clamped to a safe floor for `lose` (1500 kcal male / 1200 kcal female per profile sex) with a UI note when clamped. For `maintain`, a single computed maintenance number (TDEE) is shown. In all three goal types, the user can instead pick "set your own target" and enter a custom value (800-10000 kcal range check), which is stored with `goal_pace = 'custom'`. Accepting the plain maintenance number (not custom) stores `goal_pace = null`, since `goal_pace`'s enum (`steady`/`aggressive`/`custom`) has no value representing "the one computed maintenance option" — `null` was judged more accurate than overloading `steady` for a goal type that isn't a deficit/surplus at all.

Also converted `profiles.goal_type` from `text check (...)` to a proper `goal_type` enum (requested directly), same closed-set pattern as `ingredient_unit`. Since this changes an already-existing column's type (not a fresh migration adding new columns), the conversion drops the old check constraint and does an `alter column ... type ... using ...` cast in the new migration (`supabase/migrations/20260824000000_onboarding_profile_and_calorie_target.sql`) rather than editing the original Ticket 2 migration.

`complete_onboarding`'s parameter list grew from 5 to 10 args (name/birthdate/sex/height/weight/activity_level/goal_type/goal_weight/goal_pace/daily_kcal_target) in the same new migration; the old 5-arg signature is explicitly `drop function`-ed first since Postgres would otherwise treat the new signature as an overload rather than a replacement. `daily_kcal_target` is computed entirely client-side (`src/features/onboarding/calorieCalc.ts`) and passed straight through to the RPC with no server-side recalculation — same "client computes, RPC just persists" pattern as every other numeric field already in this function (e.g. `weight_kg`).

`useOnboardingGate`/`RequireOnboarded`/`RedirectIfOnboarded` switched their "has this user onboarded" check from `profiles.height_cm != null` to `profiles.daily_kcal_target != null` — both are set atomically in the same RPC call, but `daily_kcal_target` is the field the whole flow exists to produce, so it's the more accurate completeness signal going forward.

**Why:** Requested directly (stepper flow, calorie target, goal_type enum); `sex` and `activity_level` were added because the requested calorie math is incorrect without them, not because the original request named them.

## Fix — `group_members` RLS infinite recursion (found during Ticket 5 verification)

**Deviation:** Two of Ticket 2's RLS policies caused Postgres to report "infinite recursion detected in policy for relation group_members" on any read that touched `profiles` or `group_members` (first observed via `GET /rest/v1/profiles?select=height_cm`, i.e. `useOnboardingGate`). `"members read group membership"` (on `group_members`) queried `group_members` from inside its own `USING` clause; `"read own or group-mate profiles"` (on `profiles`) self-joined `group_members` twice, which hit that same recursive policy. Fixed in `supabase/migrations/20260821000000_fix_group_members_rls_recursion.sql` by adding `is_group_member`/`shares_group_with` `security definer` helper functions (same table-owner-bypasses-RLS pattern already used by `accept_group_invite`) and rewriting those two policies via `alter policy ... using (...)` to call them instead of self-referencing subqueries.

**Why:** Not a spec deviation so much as a correctness bug in the Ticket 2 migration's RLS gap-fill — logged here rather than editing that ticket's entry above, since this is a later migration, not a rewrite of history.

**Not yet verified:** Same database-connection restriction as above. Manual follow-up: push this migration, then retry the failing `profiles` read (e.g. reload `/onboarding` as a fresh signup) and confirm it succeeds; also spot-check a `groups`/`ingredients` read for a user in at least one group, since those policies transitively query `group_members` too.

## Ticket 7 — Recipe CRUD (personal only)

**Deviation:** This ticket's scope says "Create/edit a recipe" (unlike Ticket 6's explicit "Create/read/update/**delete**" wording for ingredients), and the Ticket 2 migration's own `recipes` RLS block only defines `select`/`insert`/`update` policies — no `delete` policy exists for `public.recipes` (confirmed by inspecting the migration directly; a note under Ticket 2 above claims a delete policy was added for `recipes`, but that's inaccurate — only `ingredients` and `recipe_ingredients` actually got one). Given both the scope wording and the missing RLS policy point the same direction, this ticket does **not** add a "delete recipe" feature — recipe deletion is left for a future ticket, along with adding the corresponding RLS policy. Removing an individual ingredient *from* a recipe (`recipe_ingredients` delete) is implemented, since that policy does exist and the acceptance criteria explicitly require verifying the kcal-recalc trigger on ingredient removal.

**Deviation:** `routes.md` lists only `/recipes` and `/recipes/:recipeId` — no creation route, same gap as Ticket 6's pantry routes. Matching that ticket's precedent, the FAB on `/recipes` opens an in-place `CreateRecipeDialog` (name/servings/photo only); on success it navigates straight to `/recipes/:recipeId` rather than back to the list, since a brand-new recipe has no ingredients yet and adding them is the very next step. `/recipes/:recipeId` handles viewing, editing recipe fields, and managing its ingredient lines.

**Deviation:** Recipe detail combines "view" and "edit" into one screen (the recipe fields render directly in an editable form, same as `IngredientDetail`) rather than a separate read-only view matching `docs/mocks/recipe-detail-*.png` pixel-for-pixel. The mockup's hero-photo + total/per-serving kcal stat tiles + ingredient list pattern is followed for layout and information hierarchy, but the "Log this recipe" CTA shown in the mockup is omitted — logging doesn't exist yet (Ticket 8).

**Why:** All three exist to satisfy this ticket's acceptance criteria (create/edit a recipe, add/remove ingredients with quantities, confirm `total_kcal` recalculates via the trigger) given routes/features later tickets haven't built yet (logging) or a schema gap the ticket's own scope suggests is intentional (recipe delete), without inventing undocumented routes or an RLS policy beyond what's specified.

**Not yet verified:** Same database-connection restriction as prior tickets — this session's tooling can't connect to a database. Manual follow-up needed (see `supabase/README.md`): create a personal recipe; add ingredients from the personal pantry with quantities and confirm `total_kcal` and per-serving kcal are correct and match a manual calculation; edit an ingredient's quantity and confirm `total_kcal` updates automatically (verifies the trigger, not client math); remove an ingredient and confirm the same; confirm the unit shown next to the quantity input in "Add ingredient" is always the selected ingredient's own unit and cannot be changed.

**Deviation (added after initial review):** The recipe detail screen (`RecipeDetail.tsx`) was reworked from "each field/ingredient change writes to Supabase immediately" to a staged-draft model: editing the name/servings/photo fields or adding/editing-quantity/removing an ingredient only updates local component state, and a single page-level "Save changes" button diffs the draft against the last-persisted snapshot and writes just the changed pieces in one batch (`Promise.allSettled` over the changed `updateRecipe`/`addRecipeIngredient`/`updateRecipeIngredientQuantity`/`removeRecipeIngredient` calls). The total/per-serving kcal stat tiles are now computed client-side from the draft ingredient list on every change (using the same formula as the `recalculate_recipe_kcal` trigger) so they update live before anything is saved, rather than reading `recipes.total_kcal` directly. After a successful save, both fields and ingredients are refetched from Supabase (so `total_kcal` still reflects the trigger's authoritative recalculation, not the client formula) and become the new baseline. This also fixed a real bug carried over from `IngredientForm`'s pattern: `submitting`/`saving` was only ever reset to `false` in the `catch` branch, never on success, so a save button that didn't navigate away afterward (as `RecipeDetail` doesn't) would stay stuck showing "Saving…" forever even after success — fixed here with `try/finally`, plus an explicit success `Snackbar` ("Recipe saved") and a persistent error `Alert` on failure, both absent before.

**Why:** Requested directly — batched/staged edits with a single explicit save, non-stuck loading state, save-result feedback, and a live-updating calorie counter are not addressed by `rpcs.md`/`frontend-architecture.md` as written for this screen.

**Not yet verified (atomicity caveat):** The batch is not transactional — `rpcs.md`'s own decision rule says multi-table/multi-row writes that must succeed or fail together should be a Postgres RPC function, but building one for this was judged out of scope for a client-side UX request. If some ops in a batch fail and others succeed, the client re-fetches the persisted state as the new baseline (so a retry only reapplies what's actually still outstanding) rather than silently losing track of a partial write, but a genuinely atomic "save recipe" RPC (mirroring `copy_recipe`'s shape) would be a more correct fix and should be considered in a follow-up ticket. Not exercised against a live Supabase project for the same database-connection-restriction reason as above.

**Deviation (added after initial review):** The "Add ingredient" dialog (`AddRecipeIngredientDialog.tsx`) gained a second mode — a "From pantry" / "New ingredient" toggle. "New ingredient" reuses the Pantry feature's own `IngredientForm` component directly (not a duplicate copy of its fields) for step one — defining and creating the ingredient (name, quantity, unit, kcal, photo), an immediate write to the personal pantry, same as `CreateIngredientDialog`. Step two, shown only after that succeeds, asks for a distinct "quantity used in this recipe" value with the now-known unit shown read-only — `IngredientForm` itself has no reason to know about this, since it's recipe-specific, not part of an ingredient's own definition. Only step two's result is staged onto the recipe draft via the same `onAdd` path "From pantry" uses, so it's still subject to the page's batched Save; the ingredient itself is already persisted regardless of whether the recipe is ultimately saved.

**Why:** Requested directly, to avoid the friction of leaving the recipe screen, creating the ingredient in Pantry, and coming back to add it.

**Not yet verified:** Same database-connection restriction as above — not exercised against a live Supabase project. ## Ticket 9 — Outbox pattern with backoff and reconnect retry (fix, found during manual testing)

**Deviation:** `frontend-architecture.md`'s Dexie schema sample indexes the `outbox` table as `'id, created_at'` only. `outbox.ts` queries it with `db.outbox.where('status').equals(...)` in three places (draining `pending`/`waiting_for_connectivity` items on reconnect/startup, counting `failed` items for `useSyncStore`) — Dexie requires a field to be indexed to `.where()` on it, so this threw `SchemaError: KeyPath status on object store outbox is not indexed` at runtime (surfaced when reconnecting after an offline test, in the `online`-event handler's `.where('status')` call). **Why:** The doc's schema sample doesn't anticipate `status`-based queries; without the index, every reconnect and every startup drain throws instead of retrying.

## Ticket 9 — Outbox pattern with backoff and reconnect retry (fix, found during manual testing)

**Deviation:** `frontend-architecture.md`'s outbox sample has no protection against the same item being drained twice concurrently. Found via manual testing: toggling network conditions back online after 5 failed auto-retries caused the queued mutation to be inserted twice server-side. Root cause — the browser (confirmed in this case via DevTools' network throttle toggle, but real network reconnects can do the same) fired the `online` event more than once for a single reconnect; `retryWaitingForConnectivity()` ran twice, each call fetched the same `waiting_for_connectivity` item and started its own independent `syncItem` call before either had deleted the row. Fixed by adding a module-level `draining` `Set<string>` of in-flight item ids in `src/sync/outbox.ts` — `drainOutboxWithRetry` and `retryFailedItem` both no-op if the item's id is already in the set, added on entry and removed on every terminal outcome (success, permanent failure, or `waiting_for_connectivity`).

**Why:** Without this, any source of a duplicate trigger (a double-fired browser event, a double-click on "Retry now", or a future caller invoking `drainPendingOutbox`/`retryWaitingForConnectivity` while a chain is already running) can double-submit a mutation with no way to detect or undo it after the fact — worse than the transient-failure problem the outbox exists to solve.

**Deviation (fix, found via screenshots — recipe totals racing on multi-ingredient saves):** The `.toFixed(0)` fix above wasn't the actual bug — reported directly with screenshots showing a genuinely different number, not a formatting mismatch: a recipe with two ingredients (150 kcal, 40 kcal) showed 190 total kcal on its own detail screen but 40 kcal on the `/recipes` list card for the exact same recipe. Root cause: `RecipeDetail.handleSave`'s ingredient-line batch (`Ticket 7`'s original design, unrelated to this ticket) built its `ops` array as `ops.push(addRecipeIngredient(...))` — calling the async function immediately, so pushing two adds (or any mix of add/remove/quantity-change) started two independent Supabase requests/transactions *concurrently*, then just waited on both via `Promise.allSettled`. The `recalculate_recipe_kcal` trigger (schema.md) recomputes `total_kcal` from scratch on every `recipe_ingredients` change by re-reading every row for that recipe at the moment it fires. Under concurrent transactions (read-committed isolation, the Postgres default), that's a lost-update race: whichever transaction's `UPDATE recipes SET total_kcal = ...` commits last wins the final value, but if *that* transaction's own `SELECT sum(...)` ran before the other transaction's insert had committed, it overwrites the correct combined total with a partial one — in the reported case, the recompute triggered by inserting the 40-kcal ingredient apparently committed last while only seeing itself, stomping the already-correct 190. `RecipeDetail`'s own stat tile never showed this, because it computes `totalKcal` live from the client's in-memory ingredient list (`ingredients.reduce(...)`), not from the persisted `recipes.total_kcal` the list card has to rely on — so the detail screen was accidentally masking a real server-side data bug.

Fixed by changing `ops` from an array of already-started promises to an array of thunks (`Array<() => Promise<void>>`), run one at a time in a `for` loop with `await` inside try/catch (preserving the original "attempt every op even if one fails, count failures" behavior, just replacing `Promise.allSettled` with a manual sequential loop) — awaiting each Supabase call guarantees its transaction (and the trigger's recompute) has fully committed before the next one starts, so every recompute after the first sees all prior changes and the final `total_kcal` ends up correct regardless of how many ingredient lines changed in one save.

**Not fully closed by this fix:** this only serializes a single save's own batch of ingredient-line ops against each other. ## Ticket 14 — Ingredient and recipe copy/fork

**Deviation (security fix):** `rpcs.md`'s own text for `copy_ingredient`/`copy_recipe` claims "RLS on the underlying insert enforces the caller must be a member of the target group" — that's incorrect for a `security definer` function, which runs as the function owner and bypasses RLS entirely on the tables it touches. Deployed as originally documented (no membership check), any authenticated caller could pass an arbitrary `p_target_group_id` and copy an ingredient or recipe straight into a group they don't belong to. `supabase/migrations/20260903000000_copy_ingredient_recipe_rpcs.sql` adds an explicit check to both functions — `is_group_member` (the same `security definer` helper already used by `group_members`'/`profiles`' RLS policies, from the Ticket 11 RLS-recursion fix) — raising an exception when `p_target_group_id` is non-null and the caller isn't a member. `find_ingredient_match` needed no such fix: it was never `security definer` in the spec, so its plain `select` is already correctly gated by the existing "read own or group ingredients" RLS policy — a caller who isn't a member of the target group just gets zero rows back, which is what makes it silently fall through to "no match, create a fresh copy" for that ingredient rather than ever exposing another group's data.

**Deviation:** `copy_recipe`'s `rpcs.md` example still selects/inserts a `servings` column. `recipes.servings` was renamed to `weight_g` in Ticket 12's own follow-up ("servings -> weight"), whose deviation log entry explicitly flagged this exact gap ("whoever implements `copy_recipe` will need to update that example to `weight_g` first"). The deployed function uses `weight_g`.

**Why (both above):** Necessary for the RPCs to be both secure and correct against the schema as it actually exists today; `rpcs.md`/`schema.md` are left unedited per this ticket's standing instruction.

**Deviation:** `routes.md`/`design-system.md` don't describe a "Copy to…" entry point anywhere. Added as a plain outlined button on `IngredientDetail`/`RecipeDetail` (`src/features/pantry/IngredientDetail.tsx`, `src/features/recipes/RecipeDetail.tsx`), alongside the existing "Delete" button — matching "detail one tap away" (design-system.md) and the precedent of putting item-level destructive/secondary actions on the detail screen rather than the list card. `RecipeDetail`'s "Copy to…" button is disabled while the screen has unsaved changes (`isDirty`) — copying always reads the last-persisted recipe/ingredients (`savedRecipe`/`savedIngredients`, refetched via `fetchRecipeIngredients`), since `recipe_ingredients` isn't staged client-side the way the recipe's own fields are (Ticket 10's "recipe_ingredients... require connectivity" split); copying while dirty would silently copy something other than what's on screen.

**Deviation:** The "Copy to…" target list (`src/features/copy/useCopyTargets.ts`) is Personal plus every group the caller belongs to (via `fetchMyGroups`, same live-Supabase pattern as `ContextSwitcher`/Ticket 11 — groups aren't mirrored in Dexie), **excluding** whichever context the item is already in. Not specified by the ticket, which only lists three supported directions (group→group, group→personal, personal→group) — copying into the exact same context isn't one of them, so it's left off the list entirely rather than allowed and left unexplained.

**Deviation:** `copy_ingredient`/`copy_recipe` write straight to Supabase (like every other RPC-backed write in this codebase — `create_group`, `accept_group_invite`, etc.), bypassing Dexie and the outbox entirely. Without further action, a copy into a group other than the one currently being viewed wouldn't show up in that group's pantry/recipes list until the next periodic pull (up to 60s, per Ticket 10's `useSyncEngine` interval) or a reconnect. Both `copyIngredient`/`copyRecipe` (`src/features/copy/api.ts`) call `pullScope` (`src/sync/pull.ts`, already exported and used internally by `useSyncEngine` — no new sync logic added) for the target scope immediately after a successful copy, so the copy appears in the target context right away.

**Deviation:** The recipe-copy confirmation step always prompts on a genuine match (same name AND same unit — `find_ingredient_match` returning any row), not conditionally based on whether `kcal_per_unit` also matches. `rpcs.md`'s "Confirmation UI contract" paragraph reads as if the prompt itself might be conditional on `kcal_per_unit` differing ("If `kcal_per_unit` differs, present two options..."), but this ticket's own acceptance criteria are unconditional ("Copying a recipe whose ingredient has an exact name+unit match... prompts the user"). Read `rpcs.md`'s `kcal_per_unit` comparison as governing what to *display* in that prompt (both values shown side by side, a warning banner surfaced only when they actually differ — `ConflictStep` in `src/features/recipes/CopyRecipeDialog.tsx`), not whether to show it at all.

**Deviation:** The recipe-copy flow resolves ingredient conflicts one at a time in a fixed sequence (a `Conflict[]` queue, `CopyRecipeDialog`) rather than one combined screen — not specified either way; chosen to keep each decision (and its kcal comparison) legible on a mobile-width screen rather than cramming an arbitrary number of conflicts into one dialog. Nothing is written server-side (no partial `copy_ingredient`/`copy_recipe` calls) until every conflict in the queue is answered and the single `copy_recipe` RPC call fires — cancelling or hitting an error at any point up to and including that final call leaves no partial copy behind, so there's no cleanup path to build.

**Deviation (fixes from the code-reviewer sub-agent pass):** The first draft of the migration only checked `p_target_group_id` membership — both `copy_ingredient` and `copy_recipe` are `security definer`, so they also bypass RLS on the *source* read (`where id = p_ingredient_id` / `p_recipe_id`), not just the target-context insert. As drafted, any authenticated caller could pass an arbitrary source id belonging to another user or group entirely and have it copied into their own context — a cross-tenant data-exfiltration path, not just a target-side authorization gap. Both functions now also check source access (owns it personally, or `is_group_member` of its group) before doing anything else, raising `'Ingredient/Recipe not found or not accessible'` otherwise.

A second, independent gap in the same draft: `copy_recipe` trusted the client-supplied `use_existing_id` in `p_ingredient_resolutions` with no server-side re-verification that it actually resolves to a visible, genuinely-matching (same name+unit) ingredient in the target context — `find_ingredient_match`'s whole purpose was being re-derived client-side and never re-checked server-side. A modified client could pass an arbitrary ingredient id as `use_existing_id`; because `recalculate_recipe_kcal` (schema.md) then runs with RLS bypassed too, that ingredient's `kcal` would leak into the new recipe's `total_kcal` as an observable side channel, and the client's own `fetchRecipeIngredients` join (`src/features/recipes/api.ts`) would throw on a `null` embed if RLS ever did block it on a subsequent read. `copy_recipe` now re-verifies `use_existing_id` server-side with the same predicate `find_ingredient_match` uses, falling back to a fresh `copy_ingredient` call (exactly as if no match had been supplied) if it doesn't check out — never raising, since a stale/bad match here isn't a caller error, just something to route around silently.

Also fixed, lower severity: both functions now raise explicitly (rather than silently returning a null id) if the source `insert ... select` matches zero rows, so a bad/deleted id slipping past the access check can't read as a successful no-op copy to the client; `find_ingredient_match`'s `kcal / quantity` now guards a zero `quantity` (no `check` constraint exists on `ingredients.quantity`) so one bad row doesn't throw for every unrelated caller who happens to look up a match against it; `CopyRecipeDialog`'s `handleConflictAnswer` gained a `useRef` guard (checked synchronously, not via `useState`, since a rapid double-tap can fire both click events before React commits the first's state update) against firing `copy_recipe` twice on a fast double-tap of the last conflict's buttons, plus a `disabled` prop on those buttons as a secondary, render-timed defense; and `copyIngredient`/`copyRecipe` (`src/features/copy/api.ts`) now swallow a `pullScope` failure that happens *after* the RPC has already committed, rather than surfacing it as a failed copy — the RPC succeeding is what matters for correctness, and a failed post-copy pull just means the target context picks it up on the next periodic sync instead of immediately.

**Why:** All fixed after the `code-reviewer` sub-agent's pass flagged them — the two access-control gaps (source-side authorization, unverified `use_existing_id`) as critical/security findings, the rest as medium/low correctness and UX gaps. Same reasoning as every prior security-relevant fix in this doc (e.g. issue #34's audit): `security definer` means RLS isn't running at all inside the function, so every externally-supplied id needs its own explicit check — it's not something "RLS already handles."

**Not yet verified:** Same database-connection restriction as every prior ticket (org policy: must not connect to databases) — the new migration hasn't been pushed or exercised against a live Supabase project, and no browser automation tooling available in this environment to drive the real auth-gated app. Verification here was `tsc -b`, `oxlint`, and `vite build`, all clean (one new instance of the pre-existing `set-state-in-effect` lint warning already present elsewhere in the codebase, in `useCopyTargets`). ## Ticket 16 — Navigation animations

**Deviation:** Built the four-tab bottom navigation bar (`src/components/BottomNav.tsx`) itself, not just the animation logic the issue text describes. `design-system.md`'s bottom nav was explicitly deferred across Tickets 6 and 11 ("no nav bar exists yet regardless — Ticket 16", "expected to land incrementally... fully wired by Ticket 16"), and there's no literal "switching bottom tabs" to animate without one. BottomNav only renders on the four tab-root screens (personal or group-scoped Pantry/Recipes/Log, plus Progress); detail screens, `/groups`, `/sync-status`, and group settings hide it, matching the native "root tab bar, pushed screens don't have one" pattern routes.md implies but doesn't spell out.

**Deviation:** Classification is a 3-way `push` / `pop` / `tab` split (`src/routes/navigationTransition.ts`), not the single `isPush` boolean in `frontend-architecture.md`'s sample. That sample's `initial`/`exit` both key off one flag, which can't produce the acceptance criteria's two *different* directions (push enters from the right; pop's exit is to the right, i.e. it must enter from the left) — a single boolean only distinguishes "sliding" from "not sliding," not which way. Classification itself is structural (is the next path a descendant of the previous one → push; the reverse → pop; both resolve to one of the four tab roots → tab; otherwise → push), not react-router's `useNavigationType()` — every "back" affordance in this app (`AppHeader`'s `onBack`, `IngredientDetailPage`/`RecipeDetailPage`/etc.) calls `navigate(path)` with a hardcoded destination, not `navigate(-1)`, so the browser history stack would report every one of those as a `PUSH`, not a `POP`; only comparing the actual pathnames gives the right answer regardless of how the navigation was triggered.

**Deviation (superseded — see the "janky" fix entry below):** The first implementation kept `AnimatePresence` but passed the transition variant through its `custom` prop (read via function-form `variants`) rather than baking it into the `motion.div`'s own `initial`/`exit` props directly as the doc sample does, specifically so a push-then-pop round trip (list → detail → back) would exit in the correct opposite directions instead of both using the direction the detail screen happened to enter with. That mechanism turned out not to work reliably in practice — see below — and `AnimatedAppShell` no longer uses `AnimatePresence` at all.

**Deviation:** FABs (`PantryList`, `RecipeList`, `DailyLog`, `GroupList`) are now wrapped in a new `FloatingPortal` (`src/components/FloatingPortal.tsx`), rendering into a `#floating-root` div added to `index.html` as a sibling of `#root`. This is the actual mechanism behind design-system.md's "FAB positioned relative to the screen root" bug this ticket calls out: Framer Motion animates `x` via a CSS `transform`, and per the CSS spec any transformed ancestor becomes the containing block for its `position: fixed` descendants — so once a page's content sits inside `AnimatedAppShell`'s animated wrapper, every FAB on it would resolve its `fixed` positioning against that wrapper instead of the viewport, permanently (not just mid-transition, since Framer Motion keeps an inline `transform` applied even at rest). Portalling out to a node that is never a descendant of the animated wrapper sidesteps the problem entirely rather than special-casing each page's layout. Pantry/Recipes/Log's FABs also moved from `bottom: 24` to `bottom: 80` to clear the new BottomNav; Groups' FAB is unchanged (`/groups` isn't a tab root, so no nav bar sits under it there).

**Deviation (fix from the code-reviewer sub-agent pass):** `classifyTransition` originally only classified `pop` for a literal parent/child pathname pair, so a "back" affordance that returns to a bottom-tab root without being that root's literal URL parent — `SyncStatusPage`'s back button (`/sync-status` → `/pantry`), `LogsPage`'s (`/logs` → `/log`), `GroupLogsPage`'s (`/logs/groups` → `/log`), `GroupSettingsPage`'s (`/groups/:id/settings` → `/groups/:id/pantry`) — fell through to the `'push'` default and slid in from the right instead of exiting to the right, violating the acceptance criteria. Fixed with one more rule: destination is a bottom-tab root and the origin isn't → `pop`. Safe as a general rule (not a per-route special case) because `BottomNav` only renders on tab-root screens, so the only way to arrive at one from a non-tab screen is that screen's own explicit back action, never a fresh forward push.

**Deviation (fix from manual testing — "the animation is janky"):** Replaced the `AnimatePresence`-based implementation entirely with a hand-rolled overlapping transition (still in `src/routes/AnimatedAppShell.tsx`, no other files affected). Two independent problems were found by instrumenting the actual DOM `transform`/`opacity` values frame-by-frame (a rAF sampler in a throwaway Playwright harness), not visible from a screenshot alone:

1. `mode="wait"` sequences exit-then-enter with nothing on screen moving together — the outgoing screen and incoming screen never share the stage, so a "slide" reads as a stutter (old vanishes, pause, new appears) rather than one continuous motion. Native stack navigation animates both screens simultaneously, one sliding fully off as the other slides fully on.
2. Worse: `AnimatePresence`'s documented mechanism for updating an *already-unmounting* child's exit animation via its own `custom` prop did not reliably land in time in practice. Sampling the real transform values showed the outgoing screen's exit target evaluating to a no-op (using the direction it *entered* with, not the one removing it — invisible, since the two happened to cancel out in the reproduced case), while the incoming screen played an unwanted two-phase animation (sliding to -48px first, then jumping to +48px and correcting back to 0) — a visibly stray extra motion cycle. This is what actually produced the reported jank, not merely the `mode="wait"` gap.

**Deviation (requested directly — deterministic object keys, replacing this ticket's original "orphaned objects accepted" design):** R2 object keys are now named by entity id (`{prefix}/{ingredient-or-recipe-id}.webp`, or the caller's own user id for avatars) instead of a random UUID, so re-uploading a photo for an existing ingredient/recipe/avatar overwrites the previous R2 object in place rather than leaving it orphaned — R2's `PUT` to an existing key replaces it natively, no explicit delete call needed. **Deviation (security, required by the change above):** Letting a client-supplied id determine which R2 object gets overwritten is only safe if that id is actually authorized — ingredient/recipe ids are visible in the URL (`/recipes/:recipeId` etc.), so without a check, any authenticated user could pass any other user's/group's ingredient or recipe id and overwrite its photo. `get-upload-url` now takes an optional `id` in its request and, for `entity: 'ingredient' | 'recipe'`, verifies it via an RLS-scoped Supabase client (the caller's own JWT forwarded as the `Authorization` header) doing `select('id').eq('id', id)` against the corresponding table before signing — confirmed by reading `supabase/migrations/20260819000000_phase1_schema.sql` that the `select` and `update` RLS policies for both tables use the byte-identical `using` predicate, so "this row is visible to the caller" is exactly equivalent to "this caller may update this row," not just an approximation. A row not found/visible returns 403. `entity: 'avatar'` never accepts a client-supplied id at all — it's always the authenticated caller's own `auth.uid()`, so a user can only ever overwrite their own avatar.

**Deviation (fix, found during this ticket's own code-reviewer pass):** The first draft of `get-upload-url` relied solely on `supabase/config.toml`'s `verify_jwt = true` to enforce `rpcs.md`'s "must be authenticated" contract. **Deviation (fix, same pass):** The presigned PUT is now signed with `content-type: image/webp` as part of the SigV4 signature (the client's fetch call already sends exactly that header), constraining the presigned URL to only accept a webp upload within its 5-minute window rather than an arbitrary file type. This doesn't validate the actual body bytes or enforce a size limit — R2 presigned PUTs don't support size-limit conditions the way S3 POST policies do, and adding that would need a materially different (POST-policy-based) upload mechanism, judged out of scope for this ticket. Accepted residual gap: a party with a valid presigned URL could PUT up to 300s worth of arbitrarily large `image/webp`-labeled bytes.

**Deviation:** The Edge Function's CORS response header is `Access-Control-Allow-Origin: *` rather than scoped to this app's specific origins — there's no existing origin-allowlist convention anywhere else in this codebase to extend, and the real access-control boundary is the auth check above, not CORS (CORS only restricts which browser-run origins can read the response; it doesn't gate the request from reaching the function). **Deviation (fix, found during this ticket's own code-reviewer pass — onboarding upload race):** The first draft's onboarding wiring let the user advance past the "About you" step (or hit "Get started") while an avatar upload was still in flight, since `AboutYouStep`'s `PhotoUpload` wasn't wired to `OnboardingStepper`'s navigation the way every other consumer (`IngredientForm`, `RecipeForm`, `RecipeDetail`, `ProfileForm`) already gates its own submit button. **Deviation (reverted — this session's own `code-reviewer` pass, before pushing):** A later request asked for `/groups/:groupId/log` and `/groups/:groupId/logs` to show every group member's own log entries regardless of context — i.e. query `log_entries` by `logged_by anyOf (group member ids)` instead of `group_id = groupId`, so a member's personal entries and other-group entries would show up too, not just what they logged into this specific group. Implemented, then reverted after the review pass found it couldn't actually work: `log_entries`' own `"read own or group log entries"` RLS policy (Ticket 2's migration) only grants visibility into a row where `logged_by = auth.uid()` OR `group_id` is one of the *caller's own* groups — there is no clause granting visibility into a fellow member's personal or other-group entries. Net effect of the reverted version: other members' personal/other-group entries still never appeared (blocked by both RLS and sync scope), while the *viewer's own* personal entries and other-groups' entries — already present locally — leaked into every group's log and per-meal breakdown unconditionally, since `logged_by = self` always matches. **Deviation (fix, found during this session's own `code-reviewer` pass):** `entry.meal_type` is typed `MealType | null`, but a `log_entries` row cached in Dexie before this feature shipped — and never re-pulled since, because `pull.ts`'s incremental cursor only re-fetches rows past their `updated_at` — actually has `meal_type === undefined` at runtime on such a row, not `null`. **Deviation (fix, same pass):** `isMealBreakdownValid`'s `sumMealKcalTargets(targets) === dailyTotal` was a strict equality check on `Number()`-parsed form strings — a typed/pasted non-integer value could make the sum land a fraction of a kcal off the daily total purely from binary floating-point rounding, even when the real-arithmetic sum is exact, incorrectly blocking a save that should have been valid. ## Community pantry (requested directly, no ticket number)

**Deviation:** Added a third ingredient visibility tier alongside the existing personal/group model (`schema.md`'s "Ownership pattern" note) — a **community** ingredient, contributed by any user and readable by every authenticated user regardless of anyone's opt-in switch, editable/deletable only by its creator. Rather than a parallel table, this is `ingredients.is_community boolean not null default false` plus a `check (not is_community or group_id is null)` constraint, deployed by `supabase/migrations/20260907000000_community_pantry.sql`. This reuses the entire existing table/RLS/Dexie/outbox/sync machinery: a community row is, structurally, just a `group_id is null` personal-shaped row, which means the existing insert/update/delete policies' `(group_id is null and created_by = auth.uid())` branch *already* grants exactly "creator-only write" with zero policy changes — only the **select** policy (`"read own or group ingredients"`) needed widening, with `or is_community = true`.

**Deviation:** `profiles.community_pantry_enabled` and `groups.community_pantry_enabled` (same migration) are the two opt-in switches — personal and per-group — gating whether community ingredients are pulled into that context's pantry list, recipe-ingredient picker, and log-entry picker. Both live directly on `/pantry`/`/groups/:id/pantry` (`PantryList.tsx`), each an immediate-save `Switch` (a `Paper` block styled like Profile's pre-existing Dark Mode switch, not a form field), not on `/profile` or the group settings screen — the requester tried folding these into `ProfileForm.tsx`/`GroupForm.tsx` first, then decided a pantry-screen switch that takes effect immediately reads better than one that only saves along with unrelated form fields the user wasn't necessarily changing. `setCommunityPantryEnabled` (`profiles/api.ts`) and `setGroupCommunityPantryEnabled` (`groups/api.ts`) are small standalone setters for this, each just a partial `.update(...)` plus the existing cache invalidation (`invalidateMyProfile`/`invalidateMyGroups`) — mirroring `updateMyProfile`/`updateGroup`'s own shape, but not routed through either full form. In group context the switch (and the toggle itself, via RLS's existing "owner manages group" policy) is owner-only — `PantryList.tsx` only renders it when the viewer's own membership role is `'owner'`, same reasoning as the settings-gear icon being owner-only elsewhere; a non-owner member sees the effect of the switch (community ingredients appearing or not) without being shown a control they couldn't use. `PantryList.tsx` holds a `pendingCommunityEnabled` local override so the switch reflects the toggle immediately rather than waiting on the profile/groups cache to re-fetch after invalidation. **Deviation:** `IngredientCard.tsx` gained an `isCommunity` prop rendering a small "Community" chip, and now always resolves `creatorName` for a community ingredient (previously `creatorName` was fetched/shown in group context only — a community ingredient's creator is meaningful information regardless of which pantry list it's surfaced in). `IngredientDetail.tsx` derives `canEdit`/`isCommunity` from the loaded ingredient row itself (`ingredient.is_community`, `ingredient.created_by === userId`), not from the route's own `groupId` — a community ingredient can be reached from `/pantry`, any `/groups/:id/pantry`, or `/community-pantry` alike, and permission has nothing to do with which of those it was opened from. A non-creator viewing a community ingredient's detail gets a read-only summary (no editable form, no Delete button) instead of the normal `IngredientForm`; "Copy to…" stays available to everyone regardless of creator, per the requester's explicit choice to allow forking a community ingredient into one's own, independently-editable personal or group pantry row (reusing the existing `copy_ingredient` RPC — only its own source-access check needed widening, see below). `useCopyTargets`/`CopyIngredientDialog` needed one real client-side change for this: their existing "exclude whichever context the item is already in" logic is wrong for a community ingredient, which isn't actually "in" whichever personal/group screen it happened to be opened from — a new `isCommunitySource` flag skips that exclusion entirely when copying from one.

**Deviation:** `copy_ingredient`/`copy_recipe`'s source-access check (`20260903000000_copy_ingredient_recipe_rpcs.sql`'s own hardening, re-declared in the new migration rather than editing that file) gained an `or is_community = true` branch so copying *from* a community ingredient is permitted for any caller — it doesn't widen what's readable (community ingredients are already select-able by everyone per the RLS change above), only what `copy_ingredient` itself, an explicit write action, will act on.

**Deviation (requested directly — delete-usage warning for a widely-shared ingredient):** `check_ingredient_usage` (`rpcs.md`) is a plain `stable` function, not `security definer` — it only ever sees recipes the caller can already read via their own RLS. For a community ingredient potentially used by other users' private recipes, that means a creator could get a false all-clear when deleting one that's actually in active use elsewhere. Rather than making the existing function privileged (which would leak other users' recipe names/existence to the deleting caller — a real exposure, not just a UX gap), added a second, `security definer` function, `check_community_ingredient_usage`, that returns only a total `count(*)` across every recipe referencing the ingredient, no names. `DeleteIngredientDialog.tsx` calls both for a community ingredient and shows them together — named recipes the caller can already see (from the existing function) plus the privileged total — so the caller learns "this affects more than you can see" without ever being shown a recipe belonging to someone they have no relationship to.

**Deviation (fix, found during this session's own `code-reviewer` pass, before pushing):** `check_community_ingredient_usage` (above) was `security definer` with no check that `p_ingredient_id` actually refers to a community ingredient — since it bypasses RLS by design, any authenticated caller could pass an arbitrary ingredient id (someone else's private personal ingredient, or another group's ingredient with no relationship to the caller) and learn its cross-user recipe-usage count, an information disclosure the existing RLS-scoped `check_ingredient_usage` deliberately can't produce. **Deviation (fix, same pass):** `CreateCommunityIngredientDialog.tsx` was a near-verbatim copy-paste of `CreateIngredientDialog.tsx` (including its `pendingId`-regeneration lifecycle comment, duplicated word-for-word) rather than parameterizing the existing dialog — the same drift risk `createIngredient` itself was already deliberately designed to avoid by taking `isCommunity` as a plain argument rather than needing a separate function. **Why:** All of the above were requested directly (the community pantry feature itself; where its two opt-in switches live, including the later move off `ProfileForm`/`GroupForm` onto `PantryList.tsx`; allowing copy-from-community; the global-count-only usage check; and the back-arrow/switch-sizing polish), except the two "fix" entries immediately above (real issues caught by this session's own `code-reviewer` subagent pass after the initial push) — see the three-question exchange this session had with the requester before finalizing the plan (entry point placement on `/pantry`/`/groups/:id/pantry` rather than a header icon; allow-copy; count-only global usage check).

## Shared kcal-per-unit helper and app-wide `.toFixed(2)` normalization (requested directly, no ticket number)
